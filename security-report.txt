NetAlertX LDAP Authentication: Comprehensive Security & Quality Report

Executive Summary
The LDAP integration in NetAlertX demonstrates solid architectural design, clean abstraction, and effective protection against common directory injection attacks. However, a critical security flaw in the implementation of the StartTLS sequence exposes service account credentials in plaintext. Additionally, the lack of default certificate validation and potential authentication downgrade risks require attention. Immediate remediation of the StartTLS flaw is necessary to ensure the secure deployment of this feature.

---

1. Critical Security Vulnerability (High Priority)

🚨 Cleartext Transmission of Service Account Credentials (StartTLS Flaw)
 * Vulnerability: In server/auth/ldap_provider.py, the _resolve_user_dn method executes the LDAP bind operation before initiating the StartTLS upgrade.
 * Mechanism:
 1   if not conn.bind():  # <-- Binds and sends credentials in cleartext
 2       return None
 3
 4   if cfg["use_start_tls"] and not cfg["use_ssl"]:
 5       conn.start_tls() # <-- Upgrades to TLS too late
 * Impact: When administrators configure LDAP to use StartTLS (typically over port 389), the LDAP_bind_dn and LDAP_bind_password are transmitted over the network in plaintext. Since service accounts often hold broad directory traversal permissions, this represents a severe credential exposure risk.
 * Remediation Plan:
     * Immediate Hotfix: Refactor server/auth/ldap_provider.py to create a single, reusable private factory method (e.g., _create_secure_connection). This method must enforce the strict operational order: initialization -> start_tls() -> bind(). This will eliminate the duplicate logic between _resolve_user_dn and _bind_as_user and guarantee the sequence is universally correct.
     * Security Advisory: Issue an advisory recommending users currently utilizing StartTLS on port 389 to temporarily switch to LDAPS on port 636 until the patch is deployed. Post-patch, users should rotate their LDAP service account passwords.
     * Regression Testing: Implement automated unit tests using unittest.mock to assert that mock_conn.start_tls.assert_called() explicitly occurs before mock_conn.bind.assert_called().

---

2. Unmitigated Risks (Medium & Low Priority)

⚠️ Missing Certificate Validation (CWE-295) - Medium Risk
 * Vulnerability: The ldap3.Server connection is initialized without a tls configuration object, meaning the SSL/TLS certificate is not validated against a trusted Certificate Authority (CA) by default.
 * Impact: Leaves the LDAP connection vulnerable to Man-in-the-Middle (MITM) attacks, allowing an attacker to intercept or spoof the LDAP server and capture user passwords.
 * Remediation Plan:
     * Introduce configuration toggles in front/plugins/auth_ldap/config.json: LDAP_tls_verify_cert (Boolean) and LDAP_ca_cert_path (String).
     * Map these in the backend to an ldap3.Tls(validate=ssl.CERT_REQUIRED, ca_certs_file=cfg["ca_cert_path"]) object.
     * Default Behavior: To maintain backward compatibility for homelab users with self-signed certificates, default LDAP_tls_verify_cert to False, but display a prominent UI warning when LDAPS/StartTLS is enabled without verification.

⚠️ Authentication Fallback Downgrade Risk - Low Risk
 * Vulnerability: If the LDAP server is unreachable or the connection times out, server/auth/manager.py falls back to evaluating local credentials.
 * Impact: A network-level attacker could intentionally drop LDAP traffic to force local authentication, facilitating brute-force attacks if a weak local admin password exists.
 * Remediation Plan:
     * UI Improvement: Rephrase the "Disable local admin account" setting in the UI to clarify the security trade-off (e.g., "Recommended for strict LDAP enforcement, but risks locking you out if the LDAP server goes down").
     * Audit Logging: Elevate the fallback logging event in server/auth/manager.py from "verbose" to "error" or "warning" so administrators can actively monitor for unexpected authentication downgrades.

3. Code Quality & Security Strengths

Despite the StartTLS sequence flaw, the codebase exhibits several strong security and architectural characteristics:

 * ✅ LDAP Injection Protection: The _escape_ldap_filter() function in ldap_provider.py strictly maps special characters (\, *, (, ), \x00) to their RFC 4515 hex equivalents. This safely sanitizes the username input, neutralizing arbitrary query injection attempts.
 * ✅ Clean Abstraction & Modularity: The LdapProvider class conforms neatly to the generic AuthProvider interface, allowing seamless strategy swapping without convoluting the core login API.
 * ✅ Error Masking: LDAP errors (e.g., unreachable servers) are logged internally but return a generic AuthResult.fail() to the frontend, preventing the leakage of directory topologies to unauthenticated users.
 * ✅ Deferred Dependency Loading: The ldap3 package is imported at runtime, preventing server startup crashes if the package is missing for users not utilizing the LDAP feature.
