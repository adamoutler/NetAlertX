### CRITICAL

**1. Denial of Service (DoS) via Synchronous Rate Limiting**
- **Location:** `server/api_server/api_server_start.py` (Line 2003)
- **Description:** The `/api/auth/login` endpoint implements a mitigation for rapid brute-force attacks by using a synchronous `time.sleep(3)` call upon authentication failure. Because the API server appears to use a synchronous worker pool (e.g., standard Flask/Gunicorn without async workers), an attacker can easily exhaust all available worker threads by sending a burst of concurrent failed login requests. This will cause the entire API server to stop responding to legitimate traffic, resulting in a Denial of Service.
- **Recommendation:** Replace the synchronous `time.sleep()` with an asynchronous delay if the framework supports it, or preferably implement an IP-based rate-limiting bucket (e.g., using Redis or an in-memory cache) that rejects requests immediately with an `HTTP 429 Too Many Requests` status code rather than tying up a thread.

### HIGH

**2. Service Account Credentials Stored in Plain Text**
- **Location:** `front/plugins/auth_ldap/config.json` & `server/auth/ldap_provider.py`
- **Description:** The system utilizes a "search-then-bind" workflow that requires a dedicated service account (`LDAP_bind_dn` and `LDAP_bind_password`). The configuration explicitly states that the password is "Stored in `app.conf`." The codebase relies on `get_setting_value("LDAP_bind_password")` without any decryption phase, indicating the password is saved in plain text. If an attacker gains read access to the file system (e.g., via directory traversal, LFI, or compromised backups), they will obtain valid Active Directory/LDAP credentials.
- **Recommendation:** Encrypt sensitive credentials at rest using a machine-specific key, or rely on Docker secrets/environment variables for sensitive injections. Alternatively, support Direct Binding (e.g., `userPrincipalName` format for AD) to eliminate the need for a service account entirely.

**3. Flawed Fallback Logic Leading to Downgrade Attacks or Lockout**
- **Location:** `server/auth/manager.py`
- **Description:** The `AuthManager` does not differentiate between an "Invalid Credential" response from the LDAP server and an "Unreachable Server" connection error. If an attacker can disrupt the network connection between NetAlertX and the LDAP server, all authentication attempts will fail over to the local database (if `disable_local_admin` is false). This is a classic downgrade attack. Conversely, if `disable_local_admin` is true, an innocent network failure will permanently lock out all administrators, as there is no documented "break-glass" procedure.
- **Recommendation:** The `LdapProvider` should return specific error states (e.g., `NETWORK_ERROR` vs `INVALID_CREDENTIALS`). Fallback to local authentication should only occur if the LDAP server is unreachable, never when the LDAP server explicitly rejects the credentials. Provide a CLI-based break-glass script for recovery.

### MEDIUM

**4. Man-in-the-Middle (MitM) Risk via Default Insecure TLS**
- **Location:** `front/plugins/auth_ldap/config.json` & `server/auth/ldap_provider.py`
- **Description:** TLS certificate verification (`tls_verify_cert`) is disabled by default (`false`) to ensure out-of-the-box compatibility for homelab users with self-signed certificates. While pragmatic, this leaves connections inherently vulnerable to MitM attacks, where an attacker on the local network could intercept the plaintext bind credentials. Furthermore, there is no UI banner or warning indicating that the current configuration is insecure.
- **Recommendation:** Provide a prominent "Security Warning" in the UI when LDAP is enabled without TLS verification. Consider implementing a "Trust On First Use" (TOFU) mechanism to fetch and pin the certificate during initial setup to make secure configurations easier.

### LOW

**5. Inadequate Audit Logging for SIEM / Fail2Ban**
- **Location:** `server/api_server/api_server_start.py`
- **Description:** Failed authentication attempts trigger a generic notification (`write_notification(f"[auth] Failed login attempt for user '{username}'", "alert")`) and verbose logging. However, neither the notification nor the log specifically captures the Source IP address of the attacker (`request.remote_addr`). This makes it practically impossible to integrate NetAlertX with external security tools like Fail2Ban or a SIEM for network-level blocking.
- **Recommendation:** Ensure that the `write_notification` and all authentication logs explicitly record the Source IP of the client attempting the login.

**6. Lack of Account Lockout Mechanism**
- **Location:** `server/api_server/api_server_start.py`
- **Description:** While the 3-second delay hinders rapid brute-forcing (at the cost of DoS), there is no sustained defense against slow "low-and-slow" credential stuffing. There is no logic to permanently lock an account or ban an IP after $N$ failed attempts.
- **Recommendation:** Implement a robust account lockout policy (e.g., 5 failed attempts locks the IP or the account for 15 minutes) natively, or rely on the Source IP logging improvement to let Fail2Ban handle it externally.
